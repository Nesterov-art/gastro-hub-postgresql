# Gastro Hub — проектирование и анализ базы данных сети общепита

Учебный проект по продвинутому SQL. Из плоских «сырых» данных о продажах
строится нормализованная схема с продвинутыми типами данных, после чего
на ней решаются семь аналитических и транзакционных задач.

**СУБД:** PostgreSQL 13
**Клиент:** DBeaver

---

## О предметной области

Gastro Hub — сеть из 80 заведений четырёх типов: кофейни, рестораны,
бары и пиццерии. Данные охватывают период с 1 января 2017 года
по 31 декабря 2023 года.

Исходные данные лежат в схеме `raw_data` в двух таблицах.

`raw_data.sales` — 204 480 строк, по одной на каждый день работы
каждого заведения:

| Поле | Тип | Описание |
|---|---|---|
| `report_date` | `date` | дата |
| `cafe_name` | `varchar` | название заведения |
| `type` | `varchar` | тип заведения |
| `avg_check` | `numeric(6,2)` | средний чек за день |
| `manager` | `varchar` | Ф. И. О. менеджера |
| `manager_phone` | `varchar` | телефон менеджера |

`raw_data.menu` — 80 строк, меню каждого заведения одним документом:

| Поле | Тип | Описание |
|---|---|---|
| `cafe_name` | `varchar` | название заведения |
| `menu` | `jsonb` | меню в виде вложенного JSON-объекта |

Меню устроено двухуровнево — категория, внутри неё блюда с ценами:

```json
{
  "Пицца": {"Маргарита": 504, "Диавола": 405},
  "Напиток": {"Кола": 120}
}
```

## Схема `cafe`

Сырые данные сильно денормализованы: имя менеджера и его телефон
повторяются в каждой из 204 тысяч строк, тип заведения хранится
произвольной строкой. Схема `cafe` приводит это в порядок.

```
cafe.restaurants                        cafe.managers
├─ restaurant_uuid  uuid  PK            ├─ manager_uuid   uuid  PK
├─ cafe_name        varchar             ├─ manager_name   varchar
├─ restaurant_type  ENUM                └─ manager_phones varchar[]
└─ menu             jsonb                        │
         │                                       │
         │        cafe.restaurant_manager_work_dates
         ├────────├─ restaurant_uuid  uuid  FK ──┤
         │        ├─ manager_uuid     uuid  FK ──┘
         │        ├─ work_start_date  date
         │        └─ work_end_date    date
         │              PK (restaurant_uuid, manager_uuid)
         │
         │        cafe.sales
         └────────├─ restaurant_uuid  uuid  FK
                  ├─ date             date
                  └─ avg_check        numeric(6,2)
                        PK (date, restaurant_uuid)
```

Ключевые решения:

- **UUID вместо автоинкремента.** Идентификатор можно сгенерировать
  где угодно, не спрашивая базу, и он не конфликтует с ключами из
  других систем — так обычно и делают в хранилищах, куда данные
  стекаются из нескольких источников. Значения выдаёт
  `gen_random_uuid()`, встроенная в ядро начиная с PostgreSQL 13.
- **ENUM `cafe.restaurant_type`.** В сыром виде тип заведения — обычная
  строка, туда можно записать что угодно. ENUM переносит проверку на
  уровень базы: некорректное значение отвергается в момент вставки.
- **Отдельная таблица периодов работы.** Менеджеров 20 на 80 заведений,
  и за семь лет они менялись — всего получилось 200 пар
  «ресторан — менеджер». Это связь «многие ко многим», хранить
  менеджера прямо в `cafe.restaurants` было бы неверно.
- **Составные первичные ключи** отражают бизнес-правила: у заведения
  за один день ровно один средний чек; работа менеджера в заведении —
  единый непрерывный период, поэтому пара «ресторан — менеджер»
  встречается один раз.
- **Массив телефонов** `manager_phones` появляется в задании 7:
  первый элемент — новый единый номер, второй — исторический.

## Структура репозитория

| Файл | Содержимое |
|---|---|
| `DDL.sql` | создание схемы, ENUM и четырёх таблиц |
| `INSERT.sql` | заполнение таблиц данными из `raw_data` |
| `task_1.sql` | представление: топ-3 заведения каждого типа по среднему чеку |
| `task_2.sql` | материализованное представление: динамика среднего чека год к году |
| `task_3.sql` | топ-3 заведения по количеству смен менеджеров |
| `task_4.sql` | пиццерии с наибольшим числом пицц в меню |
| `task_5.sql` | самая дорогая пицца каждой пиццерии |
| `task_6.sql` | повышение цен на капучино в транзакции с блокировкой строк |
| `task_7.sql` | единый номер телефона менеджеров с блокировкой таблицы |
| `comments.txt` | принятые решения и вопросы ревьюеру |

Порядок выполнения: `DDL.sql` → `INSERT.sql` → `task_1.sql` … `task_7.sql`.
Файлы заданий 6 и 7 меняют данные и структуру, поэтому запускать их
повторно без пересоздания схемы не следует.

## Что разобрано в решении

**Оконные функции.** `ROW_NUMBER()` для строгого топ-N внутри группы,
`DENSE_RANK()` там, где условие требует вывести всех при совпадении
значений, `LAG()` для сравнения показателя с предыдущим годом.
Отдельно учтено, что оконные функции вычисляются после `WHERE`,
поэтому фильтр по рангу всегда выносится на уровень выше.

**CTE и подзапросы.** Многоступенчатые расчёты разбиты на именованные
шаги через `WITH`; производные таблицы в `FROM` используются там, где
нужен `COUNT` по нескольким колонкам сразу.

**Работа с JSONB.** Извлечение по ключу операторами `->` и `->>`,
разворачивание вложенного объекта в строки через `jsonb_each_text`
(неявный `LATERAL JOIN`), точечное изменение значения внутри документа
через `jsonb_set` без перезаписи остального меню.

**Транзакции и блокировки.** В задании 6 используется блокировка
уровня строки `SELECT ... FOR UPDATE`: она запрещает параллельное
изменение обновляемых заведений, но оставляет остальные полностью
доступными и не мешает чтению. В задании 7 — табличная блокировка
`LOCK TABLE ... IN EXCLUSIVE MODE`: этот режим конфликтует со всеми
режимами кроме `ACCESS SHARE`, то есть запрещает запись, но разрешает
чтение, как и требует условие. Обоснование выбора режима в обоих
случаях вынесено в комментарии к скриптам.

**Представления.** Обычное представление — сохранённый запрос,
выполняется заново при каждом обращении. Материализованное хранит
результат физически и требует `REFRESH MATERIALIZED VIEW` для
обновления; применяется там, где расчёт тяжёлый, а данные меняются
редко.

## Результаты заполнения

| Таблица | Строк |
|---|---|
| `cafe.restaurants` | 80 |
| `cafe.managers` | 20 |
| `cafe.restaurant_manager_work_dates` | 200 |
| `cafe.sales` | 204 480 |

Перед вставкой исходные данные проверены на то, что могло бы нарушить
ограничения целостности: уникальных пар «заведение + тип» — 80,
«имя менеджера + телефон» — 20, «дата + заведение» — 204 480, то есть
столько же, сколько строк в источнике. Заведений без меню нет.
